# 以手動選擇 Reference Space 取代跨群向量檢索

產生 **Draft Reply** 時，由 Viewer 手動勾選 1~N 個 **Reference Space** 作為補充脈絡，其近期訊息連同被 @ 的討論串一起送進模型。**不建立對話向量索引、不做跨群語意檢索。**

前提是：PM 會 @ 你發問，正是因為答案不在他看得到的地方。所以草稿產生器只讀被 @ 的那個 Space 是不夠的——它只會把提問者自己講過的話換句話說。跨群脈絡是這個功能的必要條件，不是加分項。

選擇手動而非 RAG，理由是**你已經知道答案在哪個群**。這個判斷不需要 AI，而 `gemini-3.6-flash` 的輸入窗口有 1,048,576 tokens，直接吞下 2~3 個群組的近期對話綽綽有餘。向量檢索在這裡解決的是一個你其實沒有的問題。

## Consequences

- DuckDB 從架構中完全移除（`SPECIFICATION.v1.md:52`、`:81`、`:156` 曾將它列為核心元件）。
- **對話全文不需要落地。** 這連帶消除了「公司對話長期存在本機資料庫」的隱私面，以及索引同步、embedding 成本、每位 Viewer 各自維護一份索引等問題。
- 代價：你不記得答案在哪個群時，系統幫不上忙。若這件事實際發生的頻率高到造成困擾，再回頭評估 RAG——屆時它是一個增量功能，不是架構前提。
