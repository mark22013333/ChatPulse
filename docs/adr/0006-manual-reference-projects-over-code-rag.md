# 以手動登錄的參考專案取代程式碼語意檢索

Draft Reply 可以引用**實際程式碼**回答問題。程式碼來自 Viewer 事先登錄的本機 git repo，登錄時必須指定**哪個分支對應哪個環境**（正式／UAT／開發）；產草稿時由 Viewer 勾選要查哪個專案的哪個環境。**不建立程式碼索引、不做 embedding、不做語意檢索**——檢索是對指定分支跑 `git grep`，而且搜了哪些關鍵字、命中哪些檔案都會回顯給 Viewer。

前提與 ADR-0003 相同：**PM 會 @ 你問「這段邏輯為什麼這樣寫」「這是不是 bug」，正是因為答案不在他看得到的地方。** ADR-0003 讓草稿能讀別的 Space，解決了「答案在另一個群」；但有一類問題的答案不在任何 Space，而在程式碼裡——只讀對話的草稿只能把提問者的話換句話說。

選手動而非 RAG，理由與 ADR-0003 同一條：**你已經知道答案在哪個專案。** 這個判斷不需要 AI。而向量索引在這裡要付的代價（索引要跟著每次 commit 同步、每位 Viewer 各自維護一份、程式碼片段落地）換來的是一個你其實沒有的問題。

## 分支環境對應是這個功能的核心，不是設定項

**拿 UAT 的程式碼回答正式環境的 bug，會產生看起來有憑有據、實際上錯的答案**——比不回答更糟，因為附了檔案路徑與行號的答案沒有人會起疑。所以：

- `environment` 是封閉字彙 `("production", "uat", "dev")`，不接受自由文字。允許自由填，實務上必然出現 `uat`／`UAT`／`staging` 指同一個分支，而模型會照著講，於是「這是正式環境的行為」這句話就不再可信。
- 資料表的唯一鍵是 `(project_id, environment)`，一個環境一個分支。真正會問的是「正式環境跑的是哪一版？」，不會是「main 用在哪些環境？」。
- 登錄時沒有任何分支對應的專案會被**拒絕建立**。那種專案正是「查問題時找錯地方」本身。
- prompt 強制要求每個關於程式碼的說法都要指明環境、分支與 commit，並禁止跨環境混用。

## 讀程式碼一律不碰工作區

`git grep <sha>` 與 `git show <sha>:<path>`，從 object database 讀，**構造上就不可能碰到 working tree 或 index**。Viewer 的 repo 隨時可能有未提交的修改、或正在 rebase。

- `git checkout` 直接排除：會動使用者正在開發的工作區。
- `git worktree` 也不用：它對工作區安全，但要寫 `.git/worktrees/`、佔磁碟、要管生命週期、分支已被 checkout 時會失敗。它換來的是大 repo 重複查詢的速度，而這裡是「一份草稿跑幾次 grep」的互動場景。
- 環境變數設 `GIT_OPTIONAL_LOCKS=0`（不與使用者自己的 `git add` 搶 `index.lock`）與 `GIT_TERMINAL_PROMPT=0`（憑證提示會把 SSE 串流卡到逾時）。
- **分支在檢索一開始就釘成 SHA**，後續全部用 SHA。否則中途一個 `git fetch` 會讓分支移動，草稿引用的行號對不上它自己宣稱的 commit——那是最難察覺的一種錯。

## Considered Options

- **對程式碼建向量索引（RAG）**：能回答「這個功能在哪實作」這種說不出關鍵字的問題。但要處理索引與 commit 的同步、每位 Viewer 一份索引、以及程式碼片段落地——而 ADR-0003 才剛把 DuckDB 與「對話全文落地」從架構中移除。這是同一個代價換同一類收益，結論也一樣。
- **讓 LLM 規劃查詢（先問模型該搜什麼，再去 grep）**：關鍵字命中率會比啟發式高。但那是多一次模型呼叫、不可重現，而且把「AI 猜答案在哪」這個 ADR-0003 明確拒絕的性質帶回來。目前的關鍵字抽取是**刻意做笨**的啟發式（只抓 `snake_case`／`camelCase` 這類散文不會出現的形狀，扣掉會命中半個 repo 的泛用詞），補償手段是把搜了哪些詞回顯給使用者，加上 `code_terms` 覆寫與 `paths` 直接指定檔案兩個逃生門。
- **只讓使用者手動貼程式碼進來**：零風險、零實作。但那等於沒有這個功能——使用者要先知道答案在哪個檔案的哪一段，才貼得出來。

## Consequences

- **答案在沒登錄的專案裡時，系統幫不上忙。** 與 ADR-0003 完全同型的代價：使用者要先把常被問到的專案登錄一次。
- **關鍵字抽不準時會白跑一次。** 這是啟發式的必然。檢索結果條讓使用者一眼看出搜錯了，改用 `code_terms` 或直接指定檔案重跑一次即可——與「勾錯 Reference Space」是同一種回饋迴路。
- **資料邊界確實擴大，見 `SPECIFICATION.md` 10.4。** 這功能會把**公司專有原始碼片段**用個人 API key 送給 AI 供應商。10.2 當初承擔的是「所有可讀 Space 的對話」，不是這個。程式碼片段本身**不落地**（只存在請求期間的記憶體，與對話內容、圖片一致），但**草稿會落地 90 天**，而草稿裡會有檔案路徑、行號與程式碼片段。
- **機敏遮蔽是 best-effort，不是保證。** `.env`／`*.pem`／`*secret*` 這類路徑整份跳過（成本低、效果確定），存活片段內再對 `api_key|secret|password|token` 的值與常見金鑰前綴（`sk-`／`ghp_`／`AKIA`／`AIza`）做遮蔽。regex 遮蔽會漏，真正的防線是路徑排除與使用者自己的 `exclude_globs`。
- **`core` 從此有了 subprocess 依賴。** 在此之前 `core` 是純 Python ＋ HTTP。呼叫 `git` 是新的一類依賴，雖然合理（自己實作 git object 讀取很荒謬）且可關（`CODE_GIT_BIN` 可設、`CODE_ENABLED` 是總開關），但 `mcp_app` 也會繼承這個模組，所以 `code_search` 在找不到 `git` 時必須乾淨地報錯，不能在 import 時就炸。
- **`repo_path` 存但永不進 prompt。** 絕對路徑會把開發機的目錄結構送進 AI 供應商並隨草稿落地 90 天。prompt 裡一律用 repo 相對路徑。
- **要升級成 LLM 抽詞，必須先寫新的 ADR。** 那會改變「誰決定去哪裡找答案」這個性質，而那正是 ADR-0003 與本篇共同的立論基礎。
