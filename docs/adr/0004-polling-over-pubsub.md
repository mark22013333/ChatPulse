# 以輪詢偵測 Mention，不採用 Workspace Events + Pub/Sub

每 30~60 秒主動查詢一次新的 **Mention**，不使用 Google Workspace Events API 訂閱推送。

Google 確實提供了官方的推送機制，而且用使用者 OAuth 就能訂閱 `spaces/-`（所有 Space），本機程式也能以 Pub/Sub **pull** 模式消費、不必對外開 port。之所以不採用，是它的兩項附帶成本與本專案的使用情境不成比例：

1. **必須開一個啟用計費的 GCP 專案。** 用量幾乎免費，但綁信用卡是硬需求。
2. **訂閱最長 7 天後過期並自動刪除**（不帶 resource data 的情況；帶的話只有 4 小時）。續訂失敗不會報錯，只會安靜地再也收不到事件——這是最糟的失效模式。

而使用情境是「坐下來梳理 PM 的提問」，不是即時告警。Google Chat App 本來就會推播通知給你，儀表板不是你第一個知道的管道，它是你集中處理的地方。分鐘級延遲沒有實質差別。

## Consequences

- 零外部依賴，不需要 GCP 專案、不需要續訂排程。
- 配額充裕：即使退回最笨的「逐 Space 輪詢 100 個群」，一輪也只要 15~40 秒。真正的瓶頸是**每使用者 15 讀／秒**（＝900 次／分鐘），不是每專案每分鐘 3,000 次；每分鐘輪一次用掉約 11% 的瓶頸額度，仍有餘裕。
- 採集器實作為可替換介面，若日後真的需要秒級即時，換一個實作即可，資料模型與介面不動。
