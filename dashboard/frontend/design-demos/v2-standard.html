算法

oklch(L C H) → OKLab（a = C × cos H、b = C × sin H）→ 立方還原 LMS → Björn Ottosson 的 OKLab→linear sRGB 矩陣 → 分量 clamp 到 0–1 → WCAG 2.x 相對亮度 Y = 0.2126R + 0.7152G + 0.0722B（用 linear 分量，非 gamma 編碼值）→ 對比 (Y亮 + 0.05) / (Y暗 + 0.05)。以 Python 3.9 逐格算出，四捨五入至小數點後 2 位。

已檢查：本檔 36 個色值轉出的 linear sRGB 分量全部落在 0–1 內，沒有任何一個觸發 clamp， 所以不存在「超出色域被夾回去、數字虛高」的問題。

琥珀 accent 與警示色怎麼分得出來

SPEC 第 5 節點名的陷阱是：accent 取琥珀 h70、警示色取 h75，兩者在 3px 邊框或小 chip 上會分不出來。 這一版的 accent 就在 h72，所以必須正面解掉。我用了四層，前兩層完全不靠顏色：

第一層｜角色互斥（最根本的一層）。 這一版規定 accent 只能出現在「可互動 ／ 當前選取」，警示色只能出現在「證據降級」。 兩者因此永遠不會以同一種元件形態出現在同一個區塊：摘要正文左側那三種 3px 規線 （實線／虛線／點線）只用 --line-evidence 與 --caution， accent 從頭到尾不當規線用，SPEC 警告的「3px 邊框撞色」在結構上就不存在。

第二層｜線型與字符承擔主要區分（SPEC 原則 2）。 完整＝實線、降級＝虛線、缺值＝點線，每一段另外印出「完整／降級／缺值」四個字， 卡片上方還有一條常駐圖例。整份畫面轉成灰階、或給全色盲使用者看，三種狀態依然讀得出來。

第三層｜彩度差，不是色相差。 --caution 的彩度壓到 0.030（明亮）／0.034（暗色）， 而 accent 是 0.158／0.150——差 4.4～5.3 倍。 琥珀是飽和的橘黃，警示色是幾乎沒有顏色的灰褐橄欖，這個差距在 1px chip 邊框上就看得出來， 不需要放大到 3px。色相同時從 h70 推到 h95（拉開 23～33 度）當作第二重保險。

第四層｜灰階亮度也拉開。 把兩色轉成灰階後的相對亮度比：明亮主題 --signal 對 --caution 是 4.86:1， 暗色主題是 1.95:1；同尺寸的線形態 --signal-text 對 --caution 則是 1.64:1（明亮）／2.14:1（暗色）。也就是說即使完全拿掉色彩資訊， 兩者的明暗仍有可辨差距——這是第三層的補強，不是主要手段。

632px 的主內容區夠不夠用（本版最大的風險）

200px 常駐展開的主導覽把固定佔用推到 200 + 288 + 320 = 808px，1440 下主內容區只剩 632px。以 1440×900 實測（Chromium，deviceScaleFactor 2）：

42 字／行落在中文長文的舒適區間（一般建議 30～45 字），所以 632px 不是勉強夠用而是剛好。 真正被 632px 壓縮到的是工具列：三個欄位排不成一列，改成「摘要風格 ＋ 抓取則數」同列、 「AI 供應商」獨佔一列的兩列式，理由是 自動（伺服器預設：claude） 這個值本身就長。 這是本版為了換得「導覽永遠看得見文字與待處理數字」所付的代價，也是三版比較時該盯著看的地方。
